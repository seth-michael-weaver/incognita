# Engine profile: where a job's time goes (2026-11-07)

Engine: production engine-20261022-3 (nucleus 16606b356d6e, `~/fastgate_data/eng/16606b356d6e`), run the way the calculator
runs it (`scripts/talysworld/engine_job.py` / `engine_grid.py` -> `prodrun` -> `pprun.main` -> `r52pool.h_rule` +
`engine_pool.run_item` per arm), deck and inputs `~/libv02/inputs`. Laptop WSL, nice 10, one thread, warm coupled-channels
cache. Made with `scripts/perf/profile_engine.py` (plain run + py-spy `--idle --native` + cProfile, one target per fresh
process); the raw report is regenerated by

    flock /tmp/incognita_heavy.lock python3 scripts/perf/profile_engine.py --nuclides Fe-56,Au-197,U-238 --grids 1,64

Caveat on absolute seconds: the laptop was shared with other agents' test runs and with a concurrent `bench.py` run while
this was measured, so every number here is 1.2-1.8x the quiet-machine figures of the morning (Fe-56 curve 17 s here vs 8-9 s
quiet). Ratios between blocks are stable across runs; use `bench.py` on a quiet machine for headline timings.

Seconds below are wall seconds from py-spy (100 Hz, samples / rate) unless marked CPU (stagetime = the engine's own
always-on per-stage timer, `physics/hf/stagetime.py`, exclusive CPU-s inside `engine_c.run`, summed over the arms).
JS(P,A) targets (Fe-56, Au-197) run TWO arms (P and A), so every per-arm block is paid twice; U-238 (ACTJS A(rotor)) one arm.

Not in this table: `engine_job.py` (the calculator's one-energy job) first starts a SECOND interpreter,
`engine_job.cn_separation_mev`, to look up the CN separation energies for the GRIDTOP pad: 2.0-3.8 s wall, 2.8-4.2 s CPU per
job (`bench.py` arm `smin`).

So for one energy the reaction calculation proper (`engine_c.run`) is 0.4-2.0 s of an 8-12 s job: about 90 % of a
one-energy job is start-up (two interpreters, torch), the h-rule pre-runs and cache dropping. For a 64-point curve
`engine_c.run` is 43-65 % of the process.

## 5. What this says about beating TALYS

- One energy: TALYS needs 0.3-7 s for the whole process; our reaction calculation is 0.4-2 s, i.e. already competitive. The
  job loses on everything around it: ~5 s torch start-up (x2 in engine_job.py), 2-5 s of h-rule pre-runs, 1-2 s of gc. A warm
  worker that keeps the engine imported (as `engine_warm.py` already does for the grid path) and forks per job removes items 1, 3
  and 10; looking up S from the run's own cascade removes item 3 even without one.
- The h rule (item 2) recomputes `ingredients()` for the same target three times with caches dropped in between; the h of a
  given (target, deck) is a constant and can be cached on disk like the CC cache (bit-identical if stored as the repr).
- Curves: preeq + compound + multiple emission + fission are the real physics cost (8-16 CPU-s for 64 E); TALYS's
  Au-197/U-238 curves take 42/59 s, so we already win there; Fe-56 (TALYS 4-6 s) is the case to attack, where h_rule + start-up
  + gc are ~10 s of the ~17 s.
- Any change must keep `python3 scripts/perf/bench.py --gate-only` green (bit-level, rel 1e-9, against baseline.json).
